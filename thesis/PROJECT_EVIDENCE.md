## Implemented system architecture

### Backend and persistence

- FastAPI application creation, CORS, lifecycle table creation, and router registration are implemented in `backend/app/main.py:22-46`.
- Environment-driven configuration is implemented with Pydantic Settings in `backend/app/config.py:7-18`. The default database is `sqlite:///./data/papers.db`; the default local model is `qwen3:4b-instruct-2507-q4_K_M`.
- SQLModel creates tables and applies additive SQLite column migrations in `backend/app/db.py:28-113`. This is a pragmatic local migration mechanism, not a versioned migration framework.
- Persisted models exist for papers, authors, chunks, RAG answers, thesis recommendations, generated paper artifacts, topics, paper-topic links, author-topic links, and review events under `backend/app/models/`.
- JSON-like fields are stored as JSON-encoded `VARCHAR` values (`backend/app/models/paper.py:13-28`), rather than native JSON columns.

### Frontend

- The React/Vite/TypeScript frontend provides eight main views: Dashboard, Papers, Search, Ask TTLAB, Thesis Extension Finder, Topic/Author Explorer, Admin Review, and Evaluation (`frontend/src/main.tsx`).
- API calls are centralized in `frontend/src/api/client.ts`.
- The interface displays source links, chunk/page citations, grounding and review statuses, warnings, and generated-content notices in the relevant pages under `frontend/src/pages/`.
- No client-side routing package is used; the selected page is React component state. A browser refresh returns to the Dashboard.

### Deployment and operation

- `scripts/run_everything.sh:1-299` can create dependencies, prepare bounded demo data, run verification, optionally start/reuse Ollama, and serve FastAPI and Vite.
- There is no Dockerfile, Compose file, CI workflow, infrastructure-as-code configuration, production reverse-proxy configuration, or cloud deployment manifest in the audited repository.
- Production deployment is therefore **not implemented**.

## Ingestion and corpus processing

### Publication discovery and import

- `backend/app/ingestion/ttlab_page.py:28-71` implements an HTTP client with redirects, retry handling, and rate-limit/service-unavailable backoff.
- Publication records are parsed from the TTLAB WordPress archive, assigned deterministic SHA-1-based identifiers, de-duplicated by normalized title/URLs, and saved as JSON (`ttlab_page.py:74-167`, `293-369`).
- `backend/app/ingestion/manual_import.py:19-103` validates a JSON array, upserts papers and raw author-name records, preserves missing values as null/empty fields, and sets imported records to `needs_review`.
- Direct PDF downloads are dry-run by default. The downloader accepts only PDF-like URLs, checks content type and the `%PDF` signature, follows redirects, and records explicit failure states (`backend/app/ingestion/pdf_downloader.py:32-55`, `132-226`).

### PDF extraction

- PyMuPDF extracts text page by page (`backend/app/ingestion/pdf_parser.py:29-101`).
- The extractor records page count, character and word counts, empty pages, SHA-256 text hash, extraction error, and a low-text/image-heavy heuristic (`pdf_parser.py:67-98`).
- There is no OCR fallback. The low-text heuristic only warns that a PDF may be scanned (`pdf_parser.py:72-74`).

### Chunking

- Text is split by a regular-expression sentence heuristic; sentences retain page numbers (`backend/app/indexing/chunker.py:45-67`).
- The default target is 850 words, 5,000 characters maximum, and 125 overlapping words; a final chunk below 400 characters is merged (`chunker.py:79-133`).
- Section names are inferred from regular-expression matches in the first 1,200 characters and can be `Unknown` (`chunker.py:16-25`, `53-58`).
- Chunk identifiers are deterministic SHA-1-derived IDs over paper, sequence, page span, and content hash (`chunker.py:36-42`).

## Retrieval algorithms

### Keyword retrieval

- SQLite FTS5 is created when available and populated with chunk IDs, paper IDs, and text (`backend/app/indexing/keyword_search.py:69-101`).
- FTS uses the SQLite `bm25()` rank and converts it to `1 / (1 + abs(rank))` (`keyword_search.py:134-155`). This is not an independently tuned BM25 implementation.
- When FTS is unavailable or empty, a deterministic term-frequency and query-coverage score is used (`keyword_search.py:158-178`).
- Current working-tree code removes a fixed stop-word set and uses word-boundary snippet highlighting (`keyword_search.py:15-66`, `257-279`).

### Hashing-vector retrieval

- The only working embedding provider is a deterministic 256-dimensional signed feature-hashing vector (`backend/app/indexing/embedder.py:18-56`). It hashes lexical tokens with SHA-256, assigns a sign, accumulates counts, and L2-normalizes the vector.
- The `openai` and `sentence_transformers` embedding branches raise explicit runtime errors (`embedder.py:49-56`).
- Query and chunk vectors are compared with a dot product over normalized vectors, i.e., cosine similarity (`embedder.py:63-73`, `vector_store.py:14-47`).
- The system calls this path `semantic`; the thesis describes it more precisely as **hashing-vector similarity**, because it is not a learned dense semantic encoder.

### Hybrid retrieval

Current working-tree hybrid retrieval combines normalized keyword score `K`, hashing-vector score `V`, metadata match `M`, section boost `S`, evidence-quality adjustment `E`, and topical-alignment adjustment `T`:

```text
score = clip(0, 1, 0.42 K + 0.48 V + M + S + E + T)
```

Evidence: `backend/app/indexing/retriever.py:137-189`. Metadata contributes at most 0.16; section boosts depend on method/future-work/evaluation intent; evidence-quality and topical-alignment functions include hand-authored bonuses and penalties (`retriever.py:279-378`). A greedy diversity penalty reduces repeated and adjacent chunks from the same paper by up to 0.16 (`retriever.py:409-441`). Query expansion is a fixed domain dictionary, not learned relevance feedback (`retriever.py:258-268`).

These coefficients are implementation choices. There is no completed ablation study, tuning set, or statistical comparison supporting their optimality. `AUTHOR INPUT REQUIRED` for any claim that the weights were empirically optimized.

### Meaning of `grounding_status`

`backend/app/intelligence/citation_verifier.py:7-48` checks that:

1. retrieved chunks exist;
2. citations exist and map to retrieved chunk IDs;
3. required citation fields are present; and
4. token overlap between answer and cited snippets is at least 0.08.

Therefore, `grounded` is a **structural and lexical status**, not a measurement of factual correctness, entailment, answer completeness, citation correctness, or user usefulness. All 27 persisted answers are marked grounded, yet all remain unreviewed and their human-score fields are null. The thesis never converts this status into an accuracy percentage.

## Thesis Extension Finder

- Student inputs include interests, skills, time, project type, data constraints, difficulty, preferred/avoided topics, retrieval mode, and top-k (`backend/app/intelligence/extension_recommender.py:84-120`).
- The recommender retrieves up to six times the requested number of chunks and groups evidence by paper (`extension_recommender.py:139-177`, `234-252`).
- Candidate scoring is deterministic (`extension_recommender.py:24-33`, `255-295`):

| Component | Weight |
|---|---:|
| Retrieval relevance | 0.30 |
| Interest/topic lexical match | 0.20 |
| Skill match | 0.15 |
| Data feasibility | 0.10 |
| Timeline feasibility | 0.10 |
| Difficulty match | 0.10 |
| Evidence strength | 0.05 |

An avoid-topic match subtracts 0.20. Recommendations separate source-supported facts, an identified gap status (`explicit_in_paper`, `inferred_from_paper`, or `not_found`), and a system-suggested extension (`extension_recommender.py:298-400`). Verification downgrades results to partial when a gap is inferred/missing or citations do not map to retrieved chunks (`recommendation_verifier.py:6-79`).

All seven persisted runs are `partial` and `needs_review`. A disposable runtime probe returned three ranked recommendations with scores 0.5176, 0.5169, and 0.5002; only the first found an explicit gap in the retrieved evidence. These are reproducibility examples, not evidence of recommendation relevance, novelty, feasibility, or student usefulness.

## Topic and author discovery

- The explorer uses a fixed 39-rule lexical taxonomy and synonym map, not LDA, BERTopic, or a trained topic model (`backend/app/intelligence/topic_explorer.py:19-89`).
- Evidence can come from reviewed paper topics, keywords, title, venue, up to ten chunks, and generated artifacts, with hand-authored source weights (`topic_explorer.py:126-235`).
- Up to eight inferred topic links per paper are retained; author-topic scores aggregate paper-topic links (`topic_explorer.py:142-168`, `360-415`).
- Related-paper scores add shared-topic, shared-author, venue, year, lexical-overlap, and hashing-vector signals (`topic_explorer.py:661-714`).
- Author expertise wording is explicitly qualified as potential fit derived from indexed authorship and topics (`topic_explorer.py:568-590`, `652-658`).

The explorer is implemented and populated, but author duplication and the `Click to View` parsing error show that identity/expertise results are not validated.

## Generated summaries, paper intelligence, and podcast scripts

- The default artifact generator is deterministic template/extractive logic (`backend/app/intelligence/paper_artifact_generator.py`).
- It selects chunks using section and lexical priorities, generates public/technical summaries, contribution, methods, limitations, future work, suggested extensions, inferred skills, and an evaluation plan, and stores citations and warnings.
- Limitations and future work are marked `explicit`, `inferred`, or `not_found`; possible extensions are `suggested_by_system` (`paper_artifact_generator.py:325-378`, `401-496`).
- Podcast generation produces text dialogue only; no audio/TTS pipeline is implemented (`backend/app/intelligence/podcast_script_generator.py`).
- Five papers have artifact bundles and five text-only podcast scripts in the database. All 14 artifact rows require review.
